# 下一代课题验收细则

本文是[下一代课题简介](https://github.com/lsjfy-open-com/infernex-agent/blob/develop/component/InferNex-Agent/docs/architecture/next-generation-topic-and-acceptance-zh.md)的可引用验收规范，规定环境、数据、证据、量化门槛和交付边界，不建立排期。排期仍以[当前开发路线图](https://github.com/lsjfy-open-com/infernex-agent/blob/develop/component/InferNex-Agent/docs/development/roadmap-zh.md)为准。

文中阈值是开测前应冻结的验收门槛，不是已经取得的成绩。具体起步命令、文件位置、数据生成与清理步骤见[验收实验室搭建与数据指南](https://github.com/lsjfy-open-com/infernex-agent/blob/develop/component/InferNex-Agent/docs/guides/next-generation-acceptance-lab-zh.md)，可执行材料见[验收包目录](https://github.com/lsjfy-open-com/infernex-agent/tree/develop/component/InferNex-Agent/test/acceptance/next-generation)。

术语：SLO（Service Level Objective）指服务等级目标；TP（Tensor Parallelism）指张量并行；CRD（CustomResourceDefinition）指 Kubernetes 自定义资源类型；Profile 指经过验证、包含硬件和运行约束的部署规格；MCP（Model Context Protocol）提供工具接口；Skill 是带版本的领域操作指导与参考资料。Bridge 是参考实现中对推理服务进行封装管理的平台组件，不是 Kubernetes 的必需组件。

## 1. 验收类别与用例编号

验收分为“基础能力验收”和“跨环境修复与能力演进验收”两个阶段。类别与编号允许交叉引用，同一用例可以同时证明多个类别；最终以 A1–A7、B1–B11 的逐项记录为判定依据。

| 验收类别 | 基础能力验收 | 跨环境修复与能力演进验收 | 主要证明内容 |
| --- | --- | --- | --- |
| 环境识别适配 | A1、A2、A3、A7 | B1、B2、B3、B4 | 安装入口、对象与版本证据、管理权、权限、未知项和异构 Profile |
| 部署资源与流量 | A4、A5 | B3、B4、B5 | 计划、批准、资源可容纳性、候选部署、请求分流与排空 |
| 诊断证据与 SLO | A5、A7 | B8、B9 | 三态判定、请求指标、分段时序、故障真值和修复效果 |
| 修复补丁版本回退 | A4、A6 | B6、B7、B8、B9 | 候选隔离、制品校验、组合版本、漂移阻断、恢复和复验 |
| 能力构建复用治理 | A3、A6 | B2、B3、B11 | 能力/知识装配、适配合同、权限边界、候选构建和稳定发布 |
| 可视化交付可复现 | A2、A6 | B10，并覆盖全部 A/B 证据 | Dashboard、来源、环境指纹、原始证据、结果模板和接入成本 |

任何未经批准的生产变更、跨资源拥有者误写、稳定基线误删或凭据泄漏均为发布阻断项，不能由总体成功率抵消。

## 2. 通用环境、数据与证据规则

### 2.1 环境矩阵

| 环境 | 基础能力验收 | 跨环境修复与能力演进验收 |
| --- | --- | --- |
| E-N 原生环境 | 无 Bridge 的 Kind，Deployment／Service／Helm fixtures；Linux Host | 无 Bridge，原生部署和批准 Helm 写路径；同一入口至少 2 个独立 serving 实例 |
| E-M 混合环境 | Bridge 受管服务及原生工作负载并存，记录当前全局模式限制 | 同集群混合 Native／Helm／Bridge／一个有真实接口的客户 CRD 或平台；按工作负载分配管理权 |
| E-H 硬件环境 | 若有可接入的 Ascend＋Mooncake 现场则按权限采证；未提供现场时明确记为未测 | 一个 NVIDIA GPU Profile 和一个 Ascend NPU Profile 分别实机验证；不以模拟设备替代 |
| E-O 连通环境 | 安装包离线安装；已安装本地 Skill 读取 | 同一场景分别在授权联网和阻断互联网出口的内网运行；离线依赖预置，内网模型服务可用 |

测试清单须冻结 Kubernetes／Helm／引擎／驱动版本、节点及设备清单、模型与权重摘要、存储、网络、角色权限、测试负载、模型版本及模型调用 token／时间预算。CPU Kind 只验控制逻辑，不能证明 GPU/NPU 性能、RDMA、交换机行为或真实推理 SLO；小模型自动测试不能证明生产 Mooncake 已修复。

### 2.2 出题方交付责任

实施者不负责猜测测试环境、补齐未提供的真值或自行找到客户硬件。出题方至少交付下表内容：

| 交付项 | 必须描述的内容 | 当前起步材料与边界 |
| --- | --- | --- |
| CPU 控制逻辑实验室 | Host 规格、工具版本、Kind 拓扑、固定资源清单、安装／校验／清理命令 | 已提供起步配置与指南；pause 容器只用于资源识别，不能承接推理或吞吐验收 |
| 案例和数据 | 案例目标、可见输入、期望证据、隐藏真值、评分规则、hash 和许可证／授权 | 已提供三类确定性合成时间线与校验程序；只用于测试数据管线和诊断规则，不冒充真实 plog、HCCL 或交换机日志 |
| Bridge 和客户封装环境 | 实际控制器及版本、CRD/API、批准模板、实例、凭据分发与管理语义 | 可复用现有 Bridge 自动测试；真实客户框架和 B11 保留用例仍须出题方提供，贴 Helm 标签不等于真实 Helm 管理 |
| GPU/NPU/Mooncake 现场 | 实际设备、驱动、通信库、引擎版本及安装包摘要，TP/节点布局、模型挂载、内网入口、配额和测试窗口 | 起步包只提供填写与预检合同；不能从仓库推断具体机器、镜像或性能，填齐且预检通过后才能启动硬件验收 |
| 联网／断网供应清单 | 基础与目标镜像及依赖、内网模型和仓库、外部查询许可、出口阻断证据、导入渠道 | 真正离线验收须在目标环境预置全部依赖；不能只屏蔽测试 Pod 网络便声称 Host 也已隔离 |
| 实测报告与评分器 | 每项输入／输出字段、阈值、基线测量、失败／缺证规则、原始日志和校验值 | 已提供结果模板；未跑项目记为未测，空模板不能代替基线实测报告 |

硬件日志至少包括统一 UTC 时间和时钟偏差估计、request/trace ID、实例与 TP rank、prefix 命中证据、排队／提交／传输／远端完成事件、参与节点应用日志、可授权采集的 plog/通信日志，以及同时间窗 PFC/RDMA/网卡与交换机端口计数器增量。拿不到的字段须记录 `unavailable` 和原因，不能补造；局部样本不能直接拼成可靠的跨机时序。

出题方须先各校验一次已知正常和已知异常基线，确认注入可撤销、请求可复现、日志能关联。真实数据脱敏必须保持 ID 关联，并提供脱敏规则和来源授权。开发数据可公开真值；正式盲测使用未公开变体，并把答案和注入控制保存在被测方不可访问的独立账号或环境中，不能只靠不同目录名隔离。公网仓库样例不能充当隐藏评测集。

### 2.3 证据与开测门槛

每个用例至少交付测试 ID、环境指纹、被测提交及配置、命令或工具调用、预期与实测值、原始证据摘要、起止时间，以及通过／失败／未测状态。模拟测试、真实集群和真实硬件证据必须分列。没有环境的必选项算未完成，不能用截图、样例或推断代替通过记录。

开测前由出题方和验收方共同签收环境 manifest、数据清单、评分规则和基线报告。硬件、补丁依赖或客户框架未提供时，对应用例标为“未就绪”，不得向实施者宣称可复现，也不得把环境缺失算作实现失败。当前 starter kit 不代表全部 A/B 用例已经具备运行条件。

## 3. 领域模型、能力包与变更合同

### 3.1 最小领域模型

| 模型对象 | 必须包含的内容 | 决策用途 |
| --- | --- | --- |
| 环境与工作负载 | 集群身份、namespace、对象 UID、服务边界、期望配置来源 | 防止跨集群、同名重建对象和副本边界混淆 |
| 组件与管理者 | 引擎、KV 缓存、通信库、Helm／CR／平台拥有者及版本证据 | 决定诊断链路和唯一写入口 |
| 资源与 Profile | 架构、设备资源键、每实例卡数、并行方式、节点／网络／存储约束、实测容量 | 检查可容纳性，区分实例数和设备数 |
| 能力与权限 | 能发现、能读、能计划、能执行、能回退及各自依据 | 区分 unsupported、unknown、forbidden、available；能力已安装不代表可执行 |
| 目标、证据与实验 | SLO 口径、观测时间、来源、样本引用、假设和三态结果 | 证据过期则重采，资料不足不晋级 |
| 制品、版本与变更 | 基础／目标摘要、适用矩阵、Git commit、前后 snapshot、批准范围、恢复目标 | 可追溯交付、幂等执行、漂移检查和恢复验证 |

关系至少表达 `managedBy`、`dependsOn`、`runsOn`、`routesTo`、`usesArtifact` 和 `verifiedBy`。每条重要事实保留观测时间、原始对象版本或内容摘要、采集方法，以及确定／推断／未知状态；推断不能覆盖确定事实，Secret 内容不能进入公开拓扑或 Git。

例如 Helm 管理的 vLLM 服务使用 Mooncake 和挂载权重目录时，模型应关联“服务 → Helm release → 工作负载 → serving 端点 → TP workers → GPU/NPU 资源”，并记录依赖版本。升级必须通过批准的 Chart／values，不能绕过拥有者直接修改 Deployment。仅看到 Mooncake 镜像时，不能声称已经确认 KV 热路径或跨 TP 读写方式。

### 3.2 能力包与动态构建

能力包须提供识别规则、支持版本、原生对象到领域模型的映射、结构化读写接口、权限要求、操作影响、前置检查、幂等／恢复合同、Skill 和测试样例，并固定版本、摘要和依赖。支持且权限足够的能力才能启用；权限不足须显示缺口；未知客户框架进入通用只读模式并生成接入清单。客户补充 CRD schema、API 说明、脱敏样例、批准模板和恢复方法后，写能力仍须在隔离环境通过合同测试。

DeepSeek Harness 的 Cordis 插件体系、Creator 模式、工具契约、Skill provider、subagent provider 和外部 MCP 配置可用于验证“按约束组合和构建能力”的方案，不能据此推定其自动理解 Kubernetes 业务语义或已经验证生产适配器。核对依据见[官方介绍](https://deepseek.com/harness/en/)、[工具契约](https://github.com/deepseek-ai/deepseek-harness/blob/master/docs/subsystems/tools.md)、[Skill 注册](https://github.com/deepseek-ai/deepseek-harness/blob/master/docs/subsystems/skills.md)、[subagent 机制](https://github.com/deepseek-ai/deepseek-harness/blob/master/docs/subsystems/subagent.md)和[MCP 接入](https://github.com/deepseek-ai/deepseek-harness/blob/master/docs/subsystems/mcp.zh.md)。工具、Skill 和 subagent 分别是执行接口、知识指导和任务执行者，不能混作一种元数据。

动态构建验收区分三类元数据：环境元数据来自集群观测与资料核对；能力元数据描述工具 schema、Skill 适用条件和插件依赖；运行元数据记录启用版本、任务委派、权限和执行轨迹。候选构建必须在不持有生产写凭据的隔离环境完成，并经过静态检查、合同测试、独立评估者保留用例，再固化版本、摘要、依赖和适用矩阵。运行轨迹不能代替组件依赖图、现场快照或物理故障证据。

B11 的输入须包含 2 类开发用封装框架和至少 1 类保留框架；每类提供 schema、脱敏实例、管理语义、读写权限、API mock 和恢复合同，保留测试答案及故障注入真值不交给构建方。候选至少通过参数无效、缺权限、重复执行、并发漂移、取消和恢复 6 类负例；同时验证 subagent 无权限放大、取消后无遗留写任务、同一工作负载变更串行化。固定工具、仅运行时装配、允许候选构建三种方案须冻结模型、任务和 token／时间预算，报告每例成功率、总耗时、人工介入、模型调用成本、候选失败和回归数，构建费用计入总成本。

### 3.3 异构资源、在线／离线制品与可见结果

资源事实来自 Kubernetes、设备插件和获准探针；支持动态资源分配时可补充 DRA 设备信息，无支持或无权限时须说明降级。不能把“未读到设备”解释成“剩余资源为零”，也不能只按卡数推算性能，参见[Kubernetes DRA 官方说明](https://kubernetes.io/docs/concepts/resource-management/dynamic-resource-allocation/)。GPU 与 NPU 分别建立至少一个独立推理 Profile；跨节点 TP、复杂成组调度和任意 GPU/NPU 混合实例逐 Profile 增量验收，不作通用承诺。权重位置和不可变 revision 单独登记；镜像只承载引擎与依赖，权重更新默认重建或滚动替换并验证加载结果。

在线和离线方式共享同一制品清单与验收合同。断网环境不得假装已经查询上游最新版；联网环境不能用“版本更高”代替兼容性证明。互联网出口和内网模型入口分别验证。补丁清单须关联基础与目标镜像 digest、源码提交／补丁差异、架构、引擎／通信库／驱动约束、依赖、来源校验、实验结果和恢复方式。OCI 清单只提供摘要引用基础，不能替代兼容性和功能验证，参见[OCI Image Manifest](https://specs.opencontainers.org/image-spec/manifest/)。

目标缺少基础层时，离线包须携带完整所需层，不承诺所有 patch 都很小。损坏包、错误架构、基础版本不符、依赖缺失、来源验证失败均须在修改前阻断。在线与离线导入同一制品时，目标 digest 和验收合同必须一致。驱动、固件和交换机问题可形成有依据的人工处置单，不能包装成普通容器补丁自动应用。

Dashboard 至少展示环境拓扑和未知项、组件与管理者、资源和实例规模、工具／知识包可用性、原始模板／Helm values 的登记来源及修订、当前生效 YAML、SLO 基线与候选结果、补丁库存、发布／恢复状态。原始配置路径只来自明确登记或实际可读来源，缺失时显示“未知”，不能从当前对象猜测。Git 保存期望配置，snapshot 保存可核验现场状态，组合版本清单关联二者以及镜像、权重和验收证据；恢复须经资源拥有者执行并重新验证业务。

## 4. 基础能力验收

| ID | 用例与环境 | 量化门槛与交付物 |
| --- | --- | --- |
| A1 安装兼容 | E-N／E-O；Host 首装、升级、普通 HOME、sudo HOME、常规 admin 路径、失效环境候选回退、显式错误参数 | 正向和反向至少 8 个固定用例，预期结果 100% 一致；默认不要求 kubeconfig 参数；显式错误不改选集群；Linux amd64/arm64 分列实装或仅构建证据 |
| A2 通用只读与 Dashboard | E-N；原生对象、Helm 元数据、日志、Service 后端、只读权限不足 | 至少 10 个资源／错误 fixtures 结果正确；后端配置检查保持 `trafficVerified=false`；不得将裁剪 YAML 显示为原始 Chart；秘密值泄漏 0 次 |
| A3 身份与批准 | normal/root × manual/full，读命令、采集、部署、压测及未知命令 | 至少 12 个批准／拒绝测试结果正确；集群影响操作未批准执行 0 次；本机 UID 不冒充远端身份或 Kubernetes 权限 |
| A4 受管实验 | E-M；Bridge 基线、独立候选，Ready 成功、候选失败、源对象漂移 | 三类测试各重复 3 次；仅撤销本次拥有的候选；基线误删 0 次，漂移时停止并报告 |
| A5 基础 SLO | E-M 或接口 fixtures；固定串行、非流式请求；通过、退化、证据不足 | 三态各至少 3 个确定性用例判定正确；真实模型另跑一次批准的有界实验；记录完整响应 p95、成功率、串行成功请求／秒，不宣称 TTFT、TPOT 或饱和吞吐 |
| A6 记录与知识 | Git／snapshot record/list/show/verify；报告／记忆；本地 Skill 和引用读取 | 合法记录可查，至少 3 种证据篡改被检出；验证不修改集群；知识来源和摘要可查，知识文件不得获得执行权限 |
| A7 现场诊断边界 | E-H；Host／SSH／Pod plog、PFC 等采集 | 对每种现场具备条件的通道各完成一次有时间戳采集；不可用通道返回原因；阶段成果是证据链和缺口，不要求证明交换机根因或自动修复 |

本阶段出口是一份能力与未测项清单、一组可重复测试记录和一份已知限制。测试代码存在、一次自动化运行通过、现场验收通过是三种不同证据。原生写路径、通用补丁更新和自动恢复不计入本阶段已完成范围。

## 5. 跨环境修复与能力演进验收

| ID | 测试场景 | 量化门槛 |

### 5.1 指标口径

识别 precision = 正确识别条目／所有已给出的识别结果条目；recall = 正确识别条目／冻结真值中应识别且授权可见条目。版本和管理者也属于结果字段。已支持对象错标未知算漏报；未知和权限不足另设必测集合，不能剔除困难样本提高分数。误写不能被总体 95% 掩盖。

TTFT 为首 token 延迟；TPOT 为首 token 后每输出 token 的平均耗时。B8 除端到端延迟外还须保存 TTFT、TPOT、请求成功率、正确输出 token／秒和满足全部 SLO 的有效请求／秒，且不能混用单位。健康基线须是开测前冻结的健康稳定部署；健康基线、故障基线和候选须使用相同模型、权重 revision、精度、硬件资源预算及工作负载分布，并固定输入输出长度、前缀命中率和冷热缓存条件。对照顺序交替，避免缓存预热制造假改善。

B8 的健康保护与故障改善是两条独立比较，不能互换基线或混合样本。对健康基线 `H`、故障基线 `F` 和候选 `C`，健康保护逐组检查 `T_eff(C) / T_eff(H) > 0.8`、`p95_TTFT(C) / p95_TTFT(H) < 1.2` 和 `p95_TPOT(C) / p95_TPOT(H) < 1.2`；故障改善逐组检查 `1 - p95_E2E(C) / p95_E2E(F) ≥ 0.20`。其中 `T_eff` 是满足全部绝对 SLO 的有效请求／秒。达到健康保护下限只证明没有超过允许退化，不能据此宣称性能优化；优化结论必须来自对应故障基线的改善比较。任一公式分母为零或缺失，或流式请求没有有效 TPOT 样本时，该组证据不足，不能判定通过。

两条比较各自每组单独判定，不得合并三组掩盖某组退化。延迟与成功率可使用固定的同负载请求点；吞吐能力须另用开测前预注册的固定负载曲线测量，冻结各负载点、持续时间和取值方法，防止低负载掩盖容量下降。每组报告各侧请求总数、失败数、指标点估计、原始样本引用和置信区间；这些比值是预注册的验收阈值，不构成统计非劣性声明，也不得测后更换评价方法。每侧至少固定 CPU/内存 requests 与 limits、设备型号与数量、实例数和最长运行时间；未测功耗时不得声称节能。20% 改善只适用于开测前选定、有真实可修复瓶颈的案例，不构成对所有环境的承诺。成本目标可在开测前另签，并冻结延迟和质量护栏，不能测后挑选指标。

投机解码是可选专项扩展，不是 B8 默认必选项。仅当开测前已纳入方案，且待比较的基线与候选启用同一投机配置时，才比较投机性能和接受率；接受率 `A = 已接受草稿 token 数 / 已提议草稿 token 数`，不得要求无投机运行提供接受率。如比较投机加速收益，须把基线和候选分别与各自的无投机运行配对归一化：吞吐收益可取 `G_X = T_eff(X_spec) / T_eff(X_no-spec)`，延迟收益可取 `G_X = p95_E2E(X_no-spec) / p95_E2E(X_spec)`，二者选用的指标、方向、阈值、样本量和评价方法均须开测前约定并记录，再比较候选与相应基线的 `G` 和 `A`。未签署该专项时不得用投机指标替代上述健康保护或故障改善门槛。

B9 的故障真值由评估者封存，被测方不可读取注入标签。软件修复须在同负载复测并完成恢复演练。B9 可与 B8 复用软件案例；网络／交换机案例须独立判断归因证据。

## 6. 交付边界

必选交付物包括领域 schema 与迁移规则、适配器 SDK／合同测试、能力与知识包清单、两类硬件 Profile、在线／离线制品和兼容清单、组合版本／恢复记录、Dashboard、两个阶段的测试报告和实测指标表。

自动生成后直接信任未知框架写工具、通用重型本体推理平台、任意源码／算子自动优化、通用驱动／固件／交换机在线刷写、任意混合设备 TP、自行开发新调度器或 L7 数据面、无边界全自动生产批准均不在本验收范围内。
