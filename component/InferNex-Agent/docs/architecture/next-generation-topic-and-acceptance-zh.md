# 课题简介：面向异构 Kubernetes 推理集群的跨环境自动部署 Agent

研究目标：面向不同客户的推理部署环境，构建能够识别环境、规划实例规格、自动生成并执行部署方案、验证上线效果的 Agent，并支持部署后的扩缩、持续优化、版本升级与回退。故障分析服务于部署失败处理和上线保障。

本文用于课题介绍与对外引用，只说明背景、痛点、期望结果和验收类别。环境规格、案例输入、日志数据、测试步骤及量化门槛见独立的[环境与两阶段验收细则](https://github.com/lsjfy-open-com/infernex-agent/blob/develop/component/InferNex-Agent/docs/development/next-generation-acceptance-spec-zh.md)。

## 1. 背景信息

企业推理服务通常运行在 Kubernetes 集群上，但客户使用的管理方式各不相同：有的直接管理原生工作负载，有的通过 Helm 发布应用，有的使用 Operator 或自研平台统一封装。与此同时，推理引擎、缓存与通信组件、GPU／NPU 加速设备、网络拓扑和模型存储方式也存在差异。同一种模型服务的部署需求，往往需要结合具体的软件版本、资源布局和平台管理方式，重新选择模板、参数与执行接口。

客户需要的不只是自动启动容器，而是将“模型、可用资源、预期流量和 SLO”转换为可运行、可验收的部署。例如，给定模型权重和一组加速卡，需要确定每个实例的并行方式、实例数量、缓存与通信配置、存储挂载及流量分配，并在上线前确认吞吐与延迟达标。后续升级还要能够说明配置和制品变化，并恢复到已验证的稳定版本。

本课题以[智谱公开的推理基础设施 Agent 案例](https://z.ai/blog/glm-built-its-inference-infrastructure)作为工程优化方向的研究参照，研究部署适配、计算与通信配置以及性能验证如何形成连续工程流程。能力组织方面，参考 [DeepSeek Harness](https://deepseek.com/harness/en/) 的插件组合、工具与技能扩展、子代理协作及运行记录机制。由此提出的研究方向是：在可信的环境模型和执行规则基础上，按任务组织已有能力，并将新生成的能力经过测试后沉淀为可复用组件。厂商案例和运行框架不能直接代替客户环境中的有效性验证。

术语：Kubernetes 是容器集群管理平台；Helm 用于打包和发布 Kubernetes 应用；Operator 是按期望状态持续管理应用的控制器；GPU／NPU 是不同类型的计算加速设备；SLO（Service Level Objective）指服务等级目标，例如请求成功率和延迟要求。

## 2. 痛点描述

| 客户场景中的问题 | 对部署交付的影响 |
| --- | --- |
| 客户的 Kubernetes 封装、推理框架和硬件不同，部署前依赖人工摸底 | 难以复用部署流程；不清楚管理归属时，配置可能被上层控制器覆盖 |
| 模型、资源、并行方式和 SLO 缺少统一的规格规划 | 无法可靠确定单实例卡数、副本数及流量策略，容易出现资源不足或容量浪费 |
| 模板、参数、组件依赖和启动顺序分散 | 换环境就要反复修改 YAML、查版本和手动执行命令，首次部署耗时且容易遗漏 |
| 容器就绪与服务满足业务目标之间缺少验收流程 | 无法确认真实请求成功、流量是否分散、吞吐及尾延迟是否达标 |
| 联网和离线环境的镜像、依赖与配置交付方式不统一 | 安装物料不齐或组件版本不兼容，自动部署与升级流程在客户现场中断 |
| 配置、运行快照、镜像和外部权重引用缺少组合版本管理 | 升级难以重现，不能准确恢复上一稳定部署，也难以比较迭代收益 |
| 平台接入经验和部署工具难以沉淀复用 | 每接入一种客户平台都要重复开发，新生成的工具和领域知识缺少测试与版本约束 |

## 3. 期望结果与建议

1. **形成可解释的环境认知。** 自动发现集群、工作负载、组件版本、依赖、资源和管理归属，构建轻量领域模型，保留信息来源及未知项。模型应能支撑适配和决策，无需预先建立覆盖所有领域的大型本体系统。
2. **形成可扩展的领域能力。** 按环境和任务匹配工具、Skill（领域操作指导与参考知识）和 subagent（承担子任务的代理）。MCP（Model Context Protocol，模型上下文协议）可作为工具接口。对缺失能力允许生成候选适配组件，经隔离测试和版本登记后复用；执行权限与关键约束由明确规则控制。
3. **完成跨平台部署与资源管理。** 通过原生 Kubernetes、Helm 或客户平台的适配接口执行部署、扩缩和恢复。结合经验证的硬件与运行配置确定实例规格，生成可审阅的部署模板、Helm values 或平台请求，编排依赖与启动顺序，再以真实请求检验资源约束、流量分布和服务能力。
4. **完成上线验收与持续优化。** 部署后自动验证请求正确性、成功率、吞吐、首 token 延迟及逐 token 延迟，形成上线验收记录。依据负载变化和实测结果调整实例规模与运行参数，验证优化收益。部署失败或上线退化时，采集证据并执行获准的修正或回退，无法确认时明确缺口。
5. **统一联网与离线的补丁和版本管理。** 联网环境按授权检索并核对资料，离线环境支持人工或外部工具提供资料与制品。两种环境采用一致的来源、摘要、依赖及兼容性校验，记录 Git 配置版本、状态快照和制品引用，支持受控发布与恢复。模型权重通过外部存储引用和版本标识管理，更新时安排实例重新加载或滚动替换。
6. **提供可理解、可复现的交付结果。** 展示环境关系、实例规模、部署模板及配置来源、当前表现、实验结果、补丁和版本历史；每个重要结论能够追溯到证据，每项变更能够说明执行对象、效果和恢复方法。

上述期望结果建议采用以下量化目标。它们是拟定的验收要求，不是已取得的效果；详细测试条件在验收细则中冻结。

| 目标 | 建议量化指标 |
| --- | --- |
| 环境识别与能力接入 | 对已支持且授权可观测的组件，识别精确率与召回率均 ≥95%；未知与无权限场景正确标注率 100%。资料和环境齐备后，新平台只读适配试点 ≤2 人日，含受控写入与恢复累计 ≤5 人日 |
| 部署与更新后的性能保持 | 在相同模型、权重、精度、硬件资源预算和负载条件下，相对健康稳定部署基线，有效吞吐下降 <20%，p95 TTFT 与 p95 TPOT 的增幅分别 <20%，并且仍满足业务的绝对 SLO；不能用平均延迟掩盖尾延迟退化 |
| 自动部署成功率与耗时 | 原生 Kubernetes、Helm 和客户平台三类路径各做 10 次正常首部署，总自主业务成功率 ≥95%，每类 ≥90%；固定模型 ≤20GiB 且镜像、权重已预置时，成功部署从获准执行到业务验收完成的 p95 耗时 ≤15 分钟；30 分钟仍未完成计失败 |
| 人工介入与上线验收 | 每次部署计划外人工介入 ≤1 次；规定审批次数与等待时间单列。人工修改 YAML 或手动修复才能上线的尝试，不计为自主部署成功。业务成功须通过连续 100 个正确请求及约定的绝对 SLO，不能只检查容器就绪 |
| 升级与持续优化 | 正常升级至少 20 次，自主业务成功率 ≥95%；规定失败注入用例恢复达标率 100%。上线后的配置优化按选定场景对照评估；如另行纳入瓶颈修复专项，其 p95 端到端延迟改善目标为 ≥20%，不作为所有部署场景的必选要求 |
| 流量与恢复 | 两个同规格实例在固定均衡策略、非缓存亲和负载下，各承接 40%–60% 的请求；摘流上限 60 秒。测试模型 ≤20GiB、镜像与权重已预置时，批准恢复后 ≤10 分钟恢复至约定的业务验收状态 |
| 补丁与执行可靠性 | 在线／离线导入同一制品的目标摘要一致；损坏、基础版本不符、架构错误、依赖缺失及来源不可信等规定负例在变更前阻断率 100%；未批准生产写入、越权恢复及稳定基线误删均为 0 次 |

TTFT（Time To First Token）为首 token 延迟；TPOT（Time Per Output Token）为首 token 后每个输出 token 的平均耗时；p95 是第 95 百分位。这里的比较对象是**相同模型的服务部署基线**，不是把不同基础模型直接比较。部署与升级以健康稳定部署作为性能基线；业务请求成功率须 ≥99% 且不低于基线，质量评分下降 ≤1 个百分点，资源预算不增加。性能对照至少做 3 组，每侧每组 ≥1,000 个请求。只有另行选择瓶颈修复专项时才增加故障基线比较，不能用该项替代部署验收。

若选定场景涉及投机解码，可追加“投机加速收益与草稿 token 接受率不劣化”的专项要求，在相同投机配置下比较；普通部署场景不默认承担该算法指标。具体统计方法和通过标准须在开测前约定，无投机解码的基线不比较接受率。

建议采用“稳定规则与接口 + 按需组织能力 + 实验后固化”的方式演进。领域模型约束实体关系和执行边界，运行框架负责组织工具与子任务，评测决定候选组件能否成为稳定能力。宿主机身份、集群访问权限和生产变更授权需要分别处理；影响集群正常运转的操作应纳入明确的人工判定与批准机制。

## 4. 验收类别与阶段

验收分为两个阶段：**第一阶段验证部署基础与受管发布，第二阶段验证跨环境自动部署与生命周期管理**。阶段之间沿用可比较的环境、数据和证据格式，以实际测试记录说明能力提升。

| 验收类别 | 第一阶段重点 | 第二阶段重点 |
| --- | --- | --- |
| 环境识别与适配 | 安装接入、权限边界、资源与配置发现 | 多种管理框架识别、管理归属判断与未知环境处理 |
| 部署、资源与流量 | 实例和资源状态可观察，受管候选可验证 | 异构规格规划、跨平台部署、真实分流与摘流恢复 |
| 上线验收与 SLO | 请求检查、基础对照与部署失败采证 | 业务成功率、性能达标、部署后优化与退化回退 |
| 升级、补丁与版本回退 | 变更记录、配置版本和状态快照可追溯 | 联网／离线制品一致校验、组合版本恢复与业务恢复验证 |
| 能力构建、复用与治理 | 工具和知识有明确来源及权限边界 | 新适配能力构建、独立测试、版本复用与子任务约束 |
| 可视化、交付与可复现性 | 状态、配置来源、报告和证据可理解 | 完整实验和版本过程可查看，环境及验收结果可重现 |

核心指标包括部署成功率、首次部署耗时、人工介入次数、跨环境适配成本、SLO 达标率和升级回退成功率；识别准确性、执行边界与证据完整性作为支撑要求。上述核心目标对应的完整样本要求、统计口径、阈值和不适用条件统一维护在[验收细则](https://github.com/lsjfy-open-com/infernex-agent/blob/develop/component/InferNex-Agent/docs/development/next-generation-acceptance-spec-zh.md)，不以演示效果替代量化验收。

## 5. 出题方配套与交付要求

出题方应提供可复现的环境搭建指南、固定版本与资源清单、部署需求与模板样例、公开练习案例、脱敏部署日志、独立保管的验收案例及判定依据，并明确联网范围、模型服务、硬件和实验预算。涉及真实加速卡或网络设备的指标，应提供相应设备与数据；合成日志和普通容器实验只能验证其覆盖的逻辑，不能替代真实硬件效果。

承接方交付可运行组件、领域模型与适配契约、能力包及测试、补丁与恢复记录、可视化结果和逐项验收报告。对于尚未提供的环境或数据，应明确记录缺口，不能将“未测”记为“通过”。
