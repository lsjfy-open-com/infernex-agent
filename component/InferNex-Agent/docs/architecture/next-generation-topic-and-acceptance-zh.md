# 课题简介：面向异构 Kubernetes 推理集群的环境感知与可验证运维 Agent

研究目标：面向不同客户的推理部署环境，构建能够识别环境、组织领域能力、验证修复效果并管理版本恢复的 Agent，实现部署、诊断、优化与交付的连续闭环。

本文用于课题介绍与对外引用，只说明背景、痛点、期望结果和验收类别。环境规格、案例输入、日志数据、测试步骤及量化门槛见独立的[环境与两阶段验收细则](https://github.com/lsjfy-open-com/infernex-agent/blob/develop/component/InferNex-Agent/docs/development/next-generation-acceptance-spec-zh.md)。

## 1. 背景信息

企业推理服务通常运行在 Kubernetes 集群上，但客户使用的管理方式各不相同：有的直接管理原生工作负载，有的通过 Helm 发布应用，有的使用 Operator 或自研平台统一封装。与此同时，推理引擎、缓存与通信组件、GPU／NPU 加速设备、网络拓扑和模型存储方式也存在差异。同一种部署需求或故障现象，往往需要结合具体的软件版本、资源布局和平台管理方式才能处理。

推理服务的运维目标也在变化。除了服务能启动、故障能定位，客户还关心请求成功率、响应延迟、有效吞吐和资源成本，并希望优化有依据、变更可追踪、退化能恢复。例如，缓存命中后的请求仍然超时，可能涉及应用排队、计算与传输并发、远端资源或网络路径；只观察到某个网络计数器异常，不足以确定原因，更不足以证明修复有效。

本课题以[智谱公开的推理基础设施 Agent 案例](https://z.ai/blog/glm-built-its-inference-infrastructure)作为工程优化方向的研究参照，关注从问题分析进一步走向修改、实验和效果验证。能力组织方面，参考 [DeepSeek Harness](https://deepseek.com/harness/en/) 的插件组合、工具与技能扩展、子代理协作及运行记录机制。由此提出的研究方向是：在可信的环境模型和执行规则基础上，按任务组织已有能力，并将新生成的能力经过测试后沉淀为可复用组件。厂商案例和运行框架不能直接代替客户环境中的有效性验证。

术语：Kubernetes 是容器集群管理平台；Helm 用于打包和发布 Kubernetes 应用；Operator 是按期望状态持续管理应用的控制器；GPU／NPU 是不同类型的计算加速设备；SLO（Service Level Objective）指服务等级目标，例如请求成功率和延迟要求。

## 2. 痛点描述

| 客户场景中的问题 | 对部署与运维的影响 |
| --- | --- |
| 能看到容器和节点，却不清楚上层平台、组件依赖及资源管理归属 | 修改可能被控制器覆盖；不同平台需要重复适配，环境信息也难以复用 |
| 卡数、显存、并行方式、网络和实例规模缺少统一描述 | 规格建议与实际可运行能力脱节；副本数量增加后，流量和性能未必达到预期 |
| 日志、配置、指标与请求时间线分散 | 难以区分根因、伴随现象和证据不足，诊断结论难以指导可验证的修复 |
| 工具与经验依赖人工积累，新增组件缺少可靠的能力接入路径 | 工具、领域知识和任务协作反复开发；自动生成的能力又缺少验证与版本约束 |
| 客户联网条件不同，补丁及依赖版本不一致 | 断网现场资料不足、制品不完整；联网现场也可能选到不兼容的更新 |
| 配置、运行状态、镜像与外部模型权重缺少组合版本记录 | 无法准确回答改了什么、改善多少、恢复到哪一套状态以及恢复是否成功 |

## 3. 期望结果与建议

1. **形成可解释的环境认知。** 自动发现集群、工作负载、组件版本、依赖、资源和管理归属，构建轻量领域模型，保留信息来源及未知项。模型应能支撑适配和决策，无需预先建立覆盖所有领域的大型本体系统。
2. **形成可扩展的领域能力。** 按环境和任务匹配工具、Skill（领域操作指导与参考知识）和 subagent（承担子任务的代理）。MCP（Model Context Protocol，模型上下文协议）可作为工具接口。对缺失能力允许生成候选适配组件，经隔离测试和版本登记后复用；执行权限与关键约束由明确规则控制。
3. **完成跨平台部署与资源管理。** 通过原生 Kubernetes、Helm 或客户平台的适配接口执行部署、扩缩和恢复。结合经验证的硬件与运行配置确定实例规格，以真实请求检验资源约束、流量分布和服务能力。
4. **把诊断推进到可验证的修复与优化。** 围绕 SLO 关联请求、计算、缓存、通信及网络证据，形成假设和对照实验。明确区分通过、失败和证据不足，并同时评价效果、正确性、资源消耗及人工介入成本。
5. **统一联网与离线的补丁和版本管理。** 联网环境按授权检索并核对资料，离线环境支持人工或外部工具提供资料与制品。两种环境采用一致的来源、摘要、依赖及兼容性校验，记录 Git 配置版本、状态快照和制品引用，支持受控发布与恢复。模型权重通过外部存储引用和版本标识管理，更新时安排实例重新加载或滚动替换。
6. **提供可理解、可复现的交付结果。** 展示环境关系、实例规模、部署模板及配置来源、当前表现、实验结果、补丁和版本历史；每个重要结论能够追溯到证据，每项变更能够说明执行对象、效果和恢复方法。

建议采用“稳定规则与接口 + 按需组织能力 + 实验后固化”的方式演进。领域模型约束实体关系和执行边界，运行框架负责组织工具与子任务，评测决定候选组件能否成为稳定能力。宿主机身份、集群访问权限和生产变更授权需要分别处理；影响集群正常运转的操作应纳入明确的人工判定与批准机制。

## 4. 验收类别与阶段

验收分为两个阶段：**第一阶段验证基础能力与可复现诊断，第二阶段验证跨环境修复与能力演进**。阶段之间沿用可比较的环境、数据和证据格式，以实际测试记录说明能力提升。

| 验收类别 | 第一阶段重点 | 第二阶段重点 |
| --- | --- | --- |
| 环境识别与适配 | 安装接入、权限边界、资源与配置发现 | 多种管理框架识别、管理归属判断与未知环境处理 |
| 部署、资源与流量 | 实例和资源状态可观察，受管候选可验证 | 异构规格规划、跨平台部署、真实分流与摘流恢复 |
| 诊断证据与 SLO | 采证、时间关联、基础对照与证据不足判定 | 盲测故障辨别、真实负载下修复与性能效果验证 |
| 修复、补丁与版本回退 | 变更记录、配置版本和状态快照可追溯 | 联网／离线制品一致校验、组合版本恢复与业务恢复验证 |
| 能力构建、复用与治理 | 工具和知识有明确来源及权限边界 | 新适配能力构建、独立测试、版本复用与子任务约束 |
| 可视化、交付与可复现性 | 状态、配置来源、报告和证据可理解 | 完整实验和版本过程可查看，环境及验收结果可重现 |

指标包括识别准确性、任务完成率、操作边界、服务恢复时间、性能与质量、适配成本及证据完整性。具体样本数、统计口径、阈值和不适用条件统一放在[验收细则](https://github.com/lsjfy-open-com/infernex-agent/blob/develop/component/InferNex-Agent/docs/development/next-generation-acceptance-spec-zh.md)，不以演示效果替代量化验收。

## 5. 出题方配套与交付要求

出题方应提供可复现的环境搭建指南、固定版本与资源清单、公开练习案例、脱敏日志、独立保管的验收案例及判定依据，并明确联网范围、模型服务、硬件和实验预算。涉及真实加速卡或网络设备的指标，应提供相应设备与数据；合成日志和普通容器实验只能验证其覆盖的逻辑，不能替代真实硬件效果。

承接方交付可运行组件、领域模型与适配契约、能力包及测试、补丁与恢复记录、可视化结果和逐项验收报告。对于尚未提供的环境或数据，应明确记录缺口，不能将“未测”记为“通过”。
